# Publish the Portta CLI to npm

GitHub Actions publishes the `@codions/portta` workspace to the public npm
registry. It creates immutable releases: npm never permits the same package
name and version to be published twice. The installed command stays `portta`
(see `bin` in `packages/cli/package.json`); only the registry package name is
scoped.

The package already declares the public npm registry and public access in
`packages/cli/package.json`. Its build compiles the CLI and the documentation
corpus and copies the runtime assets that `portta setup` needs. In source the
manifest version is always the local identity `0.0.0-local`: a release number
is never committed, only generated by CI (see below).

## Before the first publication

1. Create or use the npm organization that owns the `@codions` scope, and
   enable two-factor authentication for publishing. Confirm the intended
   account and scope:

   ```bash
   npm login --registry=https://registry.npmjs.org/
   npm whoami --registry=https://registry.npmjs.org/
   npm org ls codions --registry=https://registry.npmjs.org/
   ```

2. Confirm that `@codions/portta` is available to that scope, or that the
   scope already owns it. The first `npm view` can return a 404 when no
   package exists yet; do not attempt a publication until the name and owner
   are settled in npm.

   ```bash
   npm view @codions/portta --registry=https://registry.npmjs.org/
   ```

3. npm can only add a trusted publisher from an existing package's settings.
   For the first-ever publication, publish a development build from a clean
   `develop` checkout using interactive npm login and 2FA:

   ```bash
   git switch develop
   git pull --ff-only origin develop
   npm run publish:bootstrap
   ```

   The command requires a clean worktree, creates an isolated temporary
   checkout, and publishes a unique
   `0.0.0-develop.<timestamp-UTC>.sha-<sha>` version with npm tag `dev`. It runs
   the CLI checks and package smoke tests before `npm publish`, then removes
   the temporary checkout. It never changes the version in your current
   checkout. This bootstrap is the only exception; it does not require a
   permanent token.

4. On the npm package's **Settings → Publishing access**, add a trusted
   publisher with these exact values:

   | npm field | Value |
   | --- | --- |
   | GitHub owner | `codions-labs` |
   | Repository | `portta` |
   | Workflow filename | `publish.yaml` |
   | Environment | empty |
   | Allowed action | `npm publish` |

   The npm job lives in `.github/workflows/publish.yaml` itself, not in a
   reusable workflow, so the filename npm checks is exactly that one. It
   exchanges its GitHub Actions OIDC identity for a short-lived npm credential
   and needs npm 11.5.1 or later, which the job verifies. No `NPM_TOKEN` is
   required or stored in GitHub. For the strongest policy, configure npm to
   require 2FA and disallow tokens after the first successful trusted
   publication.

## Publication channels and images

`publish.yaml` resolves one identity, validates once, then publishes the npm
package (the CLI) and calls the reusable GHCR workflow for the panel image
(`ghcr.io/<owner>/portta`). The CLI is not shipped as a Docker image: install
it with npm or `npx`. Docker images cover the panel and runtime services only.
Pushes to `develop` and `main` validate with the light gate (static and unit
jobs; the pull request already ran E2E) and publish an amd64 panel image. A
GitHub Release runs the complete validation, E2E included, and publishes
amd64 and arm64 panel images, each built on a native runner and merged into
one manifest.

| Trigger | Generated version | Panel image tags | npm dist-tag |
| --- | --- | --- | --- |
| Published GitHub Release `vX.Y.Z` | `X.Y.Z` | `X.Y.Z`, `sha-<short-sha>` | `latest` |
| Push to `develop` | `0.0.0-develop.<run>.sha-<sha>` | `0.0.0-develop.<run>.sha-<sha>`, `develop`, `develop-<short-sha>`, `sha-<short-sha>` | `dev` |
| Push to `main` | `0.0.0-next.<run>.sha-<sha>` | `0.0.0-next.<run>.sha-<sha>`, `next`, `next-<short-sha>`, `sha-<short-sha>` | `next` |

Every channel publishes the tag equal to the exact generated version, because
that is what an installed runtime pulls: `portta up` reads the version the
package was built with and asks for `ghcr.io/codions-labs/portta:<version>`.
The GHCR package `portta` must be public for that anonymous pull to succeed;
package visibility is set once in the GHCR package settings, never by the
workflow.

The `v` prefix belongs only to the GitHub Release name. Docker and npm use the
normalized value without it: `v1.2.3` produces `portta:1.2.3` and
`@codions/portta@1.2.3`. `dev` tracks the tip of `develop`; `next` tracks the
tip of `main`. Both are mutable convenience pointers; use a version or SHA
image tag for a reproducible deployment.

`VERSION` is not source-controlled. The workflows generate it, together with
the manifest version (`tooling/prepare-publication.mjs`), only in their
ephemeral checkout, and the CLI build embeds it into its packaged runtime. A
source checkout uses the fixed `0.0.0-local` identity everywhere: the CLI
manifest, `portta --version`, local images and the runtime `VERSION`. A test
in `packages/cli/src/context.test.ts` refuses a release number in the
manifest.

## Publish an official release

1. Merge the release-ready changes, including `CHANGELOG.md`, then check out
   `main` and update it. Official releases must point at a commit already in
   `main`.

   ```bash
   git switch main
   git pull --ff-only origin main
   git status --short
   ```

   Continue only when the last command prints nothing.

2. Run the release gate. This is the one place where the full release suite is
   required rather than the ordinary targeted checks.

   ```bash
   npm run test:release
   ```

3. Create a published GitHub Release named `vX.Y.Z` for that commit. This is
   the release control point: the workflow accepts only stable `vX.Y.Z` tags,
   confirms the tagged commit is in `main`, generates the runtime version, and
   publishes both images and the matching npm package.

4. Wait for **Publish Portta** to succeed. It reuses the repository's
   validation workflow, then builds the CLI and runs `npm run test:package`,
   which packs the workspace, installs the tarball in a temporary directory
   outside the checkout, confirms `dist/cli.js`, `dist/documentation.json` and
   `dist/runtime/` are present, and executes `portta --help` and
   `portta --version`. `npm publish` then runs with `--ignore-scripts`, so the
   checks and build are not repeated.

5. Verify the registry record and execute the package npm served. Substitute
   the release version:

   ```bash
   npm view @codions/portta@0.1.0 version dist-tags --json
   npx --yes @codions/portta@0.1.0 --version
   ```

   The second command must print `portta 0.1.0` followed by the build time. Verify the npm package page also
   shows the intended repository and public access.

For a development build, npm resolves the moving channel explicitly:

```bash
npx --yes @codions/portta@dev --version
npx --yes @codions/portta@next --version
```

## Idempotency and troubleshooting

A published npm version cannot be reused, including after an unpublish. For a
bad release, publish a corrected higher version and use npm deprecation to
guide users away from the affected version when appropriate. Do not make an
installer point at an unpublished or missing image tag. The workflow queries
`@codions/portta@<version>` before publishing; a rerun that finds exactly that
version logs the result and skips `npm publish`.

If trusted publishing fails (including an E404/E403 on `PUT` for a package that
already exists), check that the npm package is owned by the intended account,
the GitHub owner/repository/workflow filename match the table above
(`publish.yaml`), and the workflow has
`id-token: write`. Do not add a permanent token as a first response. A token is
only a fallback when npm cannot support trusted publishing for the package; use
a granular, publish-scoped secret and document the reason before adding it.

For a version mismatch, correct the GitHub Release tag rather than editing a
checkout or a runner. The generated file is an artefact, never release state.

See npm's documentation for [publishing a package](https://docs.npmjs.com/cli/v11/commands/npm-publish/), [two-factor authentication](https://docs.npmjs.com/about-two-factor-authentication/), and [trusted publishing](https://docs.npmjs.com/trusted-publishers/).
