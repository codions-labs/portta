# Adopt a Compose project with Portta

Adoption puts an existing Compose project behind the Portta gateway: its HTTP
service gets a hostname, its databases stay private, and it runs next to
other projects with its own namespace. Portta records everything it decides
outside the project — the Runtime Plan and the generated overlay live in the
installation's state — so the project's own files never change.

You drive that with five verbs, in this order, and nothing else:

```
portta envs analyze <path> --json
portta adopt <path> --dry-run --json
portta adopt <path> [decisions]
portta runtime up <path>
portta runtime status <path>
```

Every `--json` output is `{ "schema", "version", "data" }`; read `data`.

## What you never do

- Edit the project's `compose.yaml`, `Dockerfile`, `.env` or Git history.
- Write Traefik labels, networks, `docker run` arguments or an overlay by
  hand. `portta adopt` generates the overlay; a project that wants its own is
  [manual mode](../../docs/product/guides/adopting-projects.md#manual-mode),
  which is the person's choice, not yours.
- Mount or request the Docker socket. Portta reaches Docker through its own
  filtered proxies.
- Resolve a decision Portta returned as `pending` on your own. Each one exists
  because inference would be a guess about the person's project.
- Create a second Runtime Plan for a project that has one. `runtime up`
  reuses the recorded plan; a stale plan is regenerated by Portta, not by you.

## The flow

### 1. Read the project

Read the project's instruction files first (`AGENTS.md`, `CLAUDE.md`, a
`README`). They may say which service is the HTTP surface, which port it
listens on, or that the project must stay on plain Compose.

### 2. Analyze

```
portta envs analyze <path> --json
```

Read-only. `data` names the Compose file it found, the services and what
they look like, the published host ports and who already holds them, fixed
container names, published datastores, and whether the namespace is already
in use by another checkout. When the Compose file is not `compose.yaml` in
that directory, pass `--file <path>`.

If there is no Compose file, stop: there is nothing to adopt. Say so and
name the directory you looked in.

### 3. Dry run

```
portta adopt <path> --dry-run --json
```

Nothing is written. `data.outcome` is one of:

| Outcome | Meaning | What you do |
|---|---|---|
| `isolated` | Portta can run it in its own namespace with a generated overlay | continue to step 5 |
| `not_supported` | one or more decisions are pending, or something cannot be adopted | step 4 |
| `manual` | the project owns its integration (`--manual` was recorded) | report; `runtime up` operates the project's own files |

`data.pending[]` lists every unresolved choice with `code`, `service`,
`detail` and the exact `option` that resolves it. `data.findings[]` lists
what Portta noticed and will not change (bind mounts, privileged settings).
`data.services[]` says which service is routed and on which container port.

### 4. Explain the pending decisions, then ask

Explain only what `pending` returned, in the project's terms, one decision at
a time. Do not add decisions Portta did not raise. Each code maps to one
question and one option:

| `code` | The question for the person | The option |
|---|---|---|
| `ambiguous_port` | which port is the HTTP surface of this service, or should it stay private? | `--service <name>:<port>` |
| `container_name` | may the fixed `container_name` be reset for this service, so a second environment can run? | `--remove-container-name <name>` |
| `shared_network` | is sharing this external or fixed network between environments intentional? | `--allow-shared-networks` |
| `shared_volume` | is sharing this external or fixed volume between environments intentional? | `--allow-shared-volumes` |

Two facts help the person decide, and you may state them: a project with no
HTTP service is still adopted, as a private environment; a multi-port service
stays private until one port is named.

A finding Portta reports as unsupported, such as `network_mode` on a routed
service, has no option: report it and stop. The person changes the project or
keeps it on plain Compose. Do not work around it.

Wait for the answers. Then run the dry run again with the chosen options and
confirm the outcome is `isolated` before adopting.

### 5. Adopt and start

```
portta adopt <path> [the options the person chose]
portta runtime up <path>
portta runtime status <path>
portta urls
```

`adopt` records the plan; `runtime up` validates and starts it; `urls` lists
the routed hostnames. Pass the same options to `adopt` that made the dry run
`isolated`. Never pass an option the person did not choose.

### 6. Report

Say, in this order:

1. the outcome and the Compose project name Portta derived;
2. which service is routed and its URL, and which services stay private;
3. every decision taken, in the person's words, and every finding left alone;
4. how to stop and how to recover:

```
portta runtime status <path>     # what is running
portta runtime logs <path>       # every service, interleaved
portta runtime config <path>     # the exact Compose input set Portta uses
portta runtime down <path>       # stop; the project keeps its data
```

The project still runs on plain `docker compose` without Portta: adoption
adds an overlay outside the repository and removes nothing from it.

## Common situations

| Situation | What `analyze` or the dry run shows | What you do |
|---|---|---|
| No Compose file | `analyze` fails naming the directory | stop; nothing to adopt |
| Compose older than 2.24.4 | `adopt` refuses with the required version | report; the person upgrades Compose |
| Fixed `container_name` | `pending` with `container_name` | ask; `--remove-container-name` only with a yes |
| External or fixed network / volume | `pending` with `shared_network` / `shared_volume` | ask; the option only when sharing is intentional |
| Service exposing several ports | `pending` with `ambiguous_port` | ask which port, or keep it private |
| No HTTP service at all | `isolated`, no routed service | adopt; say the environment is private |
| `network_mode` on a routed service | unsupported finding | report and stop |
| Namespace already used by another checkout | `analyze` says so | report; `--project <name>` only if the person names one |
| The project wants its own overlay | the person says so | `--manual`; see the guide's manual mode |

## After adoption

Once the environment runs, the project can be placed in a Project in the
panel. From inside the directory:

```
portta projects resolve --json
portta projects context <slug> --json
```

`resolve` says which Project the directory belongs to, or that none does;
`context` is what to read before working there. Both are read-only.

## Skill, CLI and MCP

The CLI is the contract: every rule above is enforced by `portta adopt`, not
by this text. This skill only orders the verbs and says what to ask. An agent
with `portta mcp` configured has the same facts through the panel's tools;
adoption itself is a CLI action, because it reads the project directory on
the host.

Install this skill with `npx skills add codions-labs/portta --skill
portta-adopt-compose -g`. The full contract, the compatibility rules and the
troubleshooting live in
[Add an existing project](../../docs/product/guides/adopting-projects.md).
